# Render deployment for RideForge

This guide describes a free-tier evaluation deployment. It is not a production SLA: Render free web services sleep when idle, and the combined API/worker service therefore pauses dispatch and outbox delivery while asleep. Use an always-on paid service and separate worker processes for a real operating service; obtain explicit budget approval first.

## Services

- Static site: the root `render.yaml` builds `web/` with `npm ci && npm run build`, publishes `web/dist`, and configures the SPA rewrite `/* → /index.html`. The passenger portal is `/`, the driver portal is `/driver`, and the protected admin portal is `/admin`.
- API web service: the root `render.yaml` adopts `rideforge-api-final`, uses Docker context `.` and Dockerfile `backend/Dockerfile`, and checks `/api/v1/ready`.
- The Blueprint sets both services to `main`, keeps the existing free plans, and deploys only after GitHub checks pass. It intentionally adopts only `rideforge-api-final` and `rideforge-web`; it does not create a Render database or delete historical duplicate API services.
- Before applying a Blueprint sync, inspect the Render plan and confirm it adopts exactly those two existing services, creates no new paid resources, and keeps the existing Supabase database.
- The API container supervises the C++ HTTP API, durable dispatch worker and outbox worker. If any child exits, the supervisor terminates siblings and exits nonzero so Render restarts the service. This combined process layout is only a demo compromise; Render recommends separate services, and its free web service sleeps after 15 minutes without inbound traffic.
- Normal entrypoint startup does not run migrations and does not require a database-owner connection. CI validates migration scripts against a clean ephemeral PostgreSQL database; this does not apply production schema changes. Apply production migrations through a separately approved operator procedure. The entrypoint retains an opt-in maintenance mode (`RIDEFORGE_RUN_STARTUP_MIGRATIONS=true`) that requires a protected `MIGRATION_DATABASE_URL`; leave it disabled for ordinary service startup.

## Blueprint and existing services

`render.yaml` is the source of truth for the two existing Render services. Create the Blueprint from the repository's `main` branch using the **adopt existing resources** option. Review the proposed sync before approving it. The plan must adopt the existing `rideforge-api-final` and `rideforge-web` services; do not approve a plan that creates a duplicate service, provisions a Render Postgres database, or selects a paid plan.

The Blueprint uses a password-free runtime connection template as a protected manual input. Render generates `RIDEFORGE_RUNTIME_ROLE_PASSWORD` and `RIDEFORGE_JWT_SECRET` as standard base64-encoded 256-bit values. The normal startup entrypoint URL-encodes the generated runtime password and substitutes it into `DATABASE_URL_TEMPLATE`; it does not change the Supabase role password. The generated value must already match the password stored for `rideforge_app` before the API can connect. For a controlled one-time synchronization, an operator may temporarily set `RIDEFORGE_RUN_STARTUP_MIGRATIONS=true` and provide `MIGRATION_DATABASE_URL`; the migration runner applies pending migrations and synchronizes the runtime-role password before the API starts. After proving the connection, return startup migrations to false and remove the owner URL from the normal runtime environment. Do not assume the values match without a successful authenticated database connection. Keep connection strings and generated secrets out of Git and chat.

## Required secrets and configuration

Set these as protected Render environment variables; never commit them:

| Variable | Purpose |
| --- | --- |
| `DATABASE_URL_TEMPLATE` | Private runtime Session-pooler URI using `rideforge_app.PROJECT_REF` as the username and `__RIDEFORGE_PASSWORD__` as the literal password placeholder. Copy the actual pooler host/port from Supabase Connect; do not guess the pooler cluster index. |
| `RIDEFORGE_RUNTIME_ROLE_PASSWORD` | Generated by Render as standard base64 and inserted into the runtime URI. It must already match the `rideforge_app` password in Supabase; the normal startup path does not synchronize it. The opt-in maintenance migration path can synchronize it when the owner URL is temporarily configured. |
| `MIGRATION_DATABASE_URL` | Optional private migration-owner connection used only when `RIDEFORGE_RUN_STARTUP_MIGRATIONS=true` for a controlled maintenance deployment. It is not required by normal API startup and must never be passed to API/worker processes. |
| `RIDEFORGE_JWT_SECRET` | Generated independently by Render. |
| `RIDEFORGE_USER_AGENT` | Contact-bearing identifier for the geocoding provider. |
| `RIDEFORGE_ALLOWED_ORIGINS` | Exact HTTPS origins for passenger and driver frontends; comma-separated, no wildcard. |
| `RIDEFORGE_GEOCODING_URL`, `RIDEFORGE_ROUTING_URL` | Contracted or self-hosted providers for public use. Public demo endpoints are evaluation-only. |
| `RIDEFORGE_GEOCODING_CONTEXT` | Defaults to `Noida, Uttar Pradesh, India`; applied server-side to route/fare quote requests. |
| `RIDEFORGE_GEOCODING_MIN_INTERVAL_MS`, `RIDEFORGE_ROUTING_MIN_INTERVAL_MS` | Optional provider pacing overrides in milliseconds. Public Nominatim and OSRM demo hosts default to one request per second; set according to the contracted/self-hosted provider's terms. |
| `RIDEFORGE_DISPATCH_RADIUS_KM` | Integer 1–100; default 20. |

Public Nominatim explicitly prohibits personal/confidential data and client-side autocomplete. Use public landmarks/test locations only in this demo; do not enter home addresses. For real passenger pickup/drop-off locations, use a contracted provider with appropriate privacy terms or a self-hosted geocoder.

For Supabase, open the project's **Connect** dialog and copy the actual **Session pooler** host and port. Do not construct the hostname from the region: Supabase can assign different pooler cluster indexes. Session mode uses port 5432 and supports long-lived connection features such as PostgreSQL LISTEN/NOTIFY; transaction mode (6543) does not. For `DATABASE_URL_TEMPLATE`, copy the Session-pooler connection string, replace the username with `rideforge_app.PROJECT_REF`, and replace the password with the literal `__RIDEFORGE_PASSWORD__`. For `MIGRATION_DATABASE_URL`, use the owner Session-pooler string with username `postgres.PROJECT_REF` and the actual database password. Percent-encode reserved characters in that password before inserting it into the URI (especially `@`, `:`, `/`, `?`, `#`, `&`, and spaces); never put an unescaped password into a URL. Copy the exact pooler host/port from Connect; the connected project metadata exposes only the direct database host, not the assigned pooler host. Use SSL mode `require`. The API's PostgreSQL pool is capped at 10 connections; the dispatch and outbox workers each hold an additional database connection, and migration startup uses a separate owner connection transiently. This is an intentional small-instance budget, not a guarantee that the project's pooler can serve it: verify the actual shared-pooler pool size, database max connections, and Supabase internal-service usage in Database Settings/Observability before enabling sustained traffic. Do not increase API concurrency, replicas or workers without recalculating the aggregate connection budget.

Example shapes (replace every angle-bracket value with the exact Connect details; do not use these placeholders literally):

```text
DATABASE_URL_TEMPLATE=postgresql://rideforge_app.<PROJECT_REF>:__RIDEFORGE_PASSWORD__@<SESSION_POOLER_HOST>:5432/postgres?sslmode=require
MIGRATION_DATABASE_URL=postgresql://postgres.<PROJECT_REF>:<DATABASE_OWNER_PASSWORD>@<SESSION_POOLER_HOST>:5432/postgres?sslmode=require
```

Use the project owner password only in `MIGRATION_DATABASE_URL`. Store all connection strings only in Render's encrypted environment variables. Rotate credentials if they have ever been pasted into chat, source control or logs.

## Frontend build

Set `VITE_API_BASE_URL` at build time to the API's HTTPS URL. The API's `RIDEFORGE_ALLOWED_ORIGINS` must include the exact static-site origin and the driver hostname/origin if a separate driver domain is configured. Rebuild the static site after changing this variable.

## Verification gates

1. Confirm Render's image build succeeds on the exact reviewed Git SHA.
2. Confirm API `/api/v1/health` and `/api/v1/ready` both return success.
3. Verify passenger registration/login, real provider route quote, booking, SSE updates, cancellation and history.
4. Verify driver approval, going online, fresh location, offer delivery, acceptance, decline, 45-second expiry and redispatch.
5. Verify admin provisioning, audit history and support-report triage.
6. Verify all workers remain alive, restart on failure, and shut down cleanly.
7. Verify a real backup and restore drill, alerting, privacy/deletion controls and load/reconnect tests.

Do not insert synthetic rides, drivers, payments, identity checks or support outcomes to make a demo appear operational. The project does not implement real payments, verified driver/vehicle compliance, staffed emergency response or commercial legal authorization.

When the opt-in maintenance mode is enabled, the Render entrypoint validates both connection strings before running migrations: each must require TLS (`sslmode=require`, `verify-ca`, or `verify-full`), use the shared Session pooler on port 5432, and identify the same Supabase project and exact pooler host. The runtime username must be `rideforge_app.PROJECT_REF`; the migration-owner username must be `postgres.PROJECT_REF`. Invalid or mismatched values fail startup before any migration executes. Normal startup validates and uses only the runtime template. This is intentional fail-closed behavior; do not bypass it by changing the URI to a direct endpoint or transaction-mode port.
